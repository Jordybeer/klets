# Klets v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Klets: a polished React page with a clothed candy-like 3D rear, one hand-contact animation per accepted action, and one contextually appropriate Dutch idea.

**Architecture:** A pure catalog/selection engine feeds one generator controller. React renders context, results and supporting views; a small lazily loaded Three.js stage displays controller-owned animation state. Versioned browser storage sits behind an adapter with an in-memory fallback.

**Tech Stack:** React, TypeScript, Vite, Three.js, CSS custom properties; Vitest and React Testing Library for behavior tests. npm with a committed `package-lock.json`; Node.js >=22.12. No backend or external state/motion/physics library in v1. Pin resolved dependency versions at setup; no unverified version numbers in this plan.

**Spec:** `docs/superpowers/specs/2026-10-13-klets-design.md` (v0.3), `PRODUCT.md`, `DESIGN.md`.

**Status:** Proposed build plan awaiting review; checkboxes below have not been executed. Hosting and image-comp-first versus code-first are open workflow choices and do not authorize extra infrastructure. This PR contains design and planning documents only.

## Global Constraints

- Brand: **Klets**, selected by the user. Candy-like 3D, peach/lavender, a clothed stylized object and a cartoon hand.
- Four intents: `request`, `tease`, `appreciation`, `desire`; visible labels `Opdrachtje`, `Plagen`, `Waardering`, `Verlangen`.
- Situations: `together`, `remote`; tones: `warm`, `playful`, `direct`, labeled `Lief`, `Speels`, `Direct`.
- Defaults: `together`, `playful`, `request`; sound off; system reduced-motion preference respected; motion independently pausable.
- Main layout: category grid when height permits; one 44 px category control below approximately 640 px usable content height. Compact 568 px budget: 24 + 76 + 44 + 164 + 104 + 88 + 44 + 24.
- Category selection commits immediately. Situation/tone editor uses confirmation/cancellation. Old results retain their original context and text.
- One accepted action reserves one result. Contact reveals the reserved result; duplicate contact callbacks are harmless. Zero candidates create no accepted draw or contact feedback.
- Approximately 600 ms contact/recovery; approach 40–150 ms, contact 150–190 ms, reveal 240–420 ms, recovery through 600 ms. Reduced motion preserves the result without travel or rebound.
- Target 40 distinct, non-graphic Dutch ideas per intent: 160 total. Natural short text, usually 6–18 words; no artificial variants to reach the number.
- No automatic escalation, sending, execution tracking or partner-state inference. Future points, agreements, accounts and synchronization stay out of v1.
- Follow the spec's palette and spacing. Text remains selectable DOM text, independent of WebGL and sound.
- Passing static/unit checks do not establish visual quality. Report the actual browser/asset verification scope.

## Review Focus

1. Filter changes during a running draw preserve the reserved text/context; tests in Task 1 and Task 3.
2. Hidden tabs, supporting views and reduced motion finalize an accepted draw exactly once; tests in Task 3 and Task 4.
3. Clipboard/storage denial and unknown stored versions preserve a usable session without false persistence claims; tests in Task 2 and Task 3.
4. Very short viewports, zoom and disappearing focus openers retain reachable controls and understandable return paths; tests in Task 3 plus visual checks in Task 5.
5. Empty/single-idea pools, catalog changes and cross-filter repetition remain explicit and never widen filters silently; tests in Task 1.

## Task 1: Catalog and selection engine

**Files:** setup files; all catalog/engine files listed above. `src/main.tsx` may use a minimal temporary entry until Task 3 supplies `App`; no marketing content or fake completed UI.

**Interfaces:**

- `Intent = 'request' | 'tease' | 'appreciation' | 'desire'`; `Situation = 'together' | 'remote'`; `Tone = 'warm' | 'playful' | 'direct'`.
- `Selection = { situation: Situation; tone: Tone; intent: Intent }`.
- `Idea = { id: string; text: string; intent: Intent; situations: Situation[]; tones: Tone[]; status: 'approved'; qualification?: string }`.
- `ResultSnapshot = { actionId: string; ideaId: string; text: string; intent: Intent; selection: Selection; drawnAt: number }`.
- `PoolState = { catalogVersion: string; remainingIds: string[] }`.
- `eligibleIdeas(catalog: readonly Idea[], selection: Selection): Idea[]`.
- `reserveIdea(catalog: readonly Idea[], selection: Selection, pool: PoolState | undefined, lastShownId: string | null, random: () => number): { idea: Idea | null; pool: PoolState }`.

- [ ] Write `selection.test.ts` with named tests: `filtersExactSelection`, `emptyPoolReturnsNull`, `singlePoolIsExplicit`, `exhaustionReshuffles`, `avoidsLastShownWhenPossible`, `catalogChangeRemovesStaleIds`. Use a small synthetic catalog with one excluded situation and one excluded tone; assert no filter widening. Assert no repeated ID during an uninterrupted cycle. Specify the spec's cross-filter boundary exception without silently dropping an eligible ID forever.
- [ ] Run `npm test -- src/features/inspiration/selection.test.ts`; establish a meaningful failing test before the engine implementation.
- [ ] Set up React/TS/Vite and the test command, implement the interfaces, then author `catalog.ts` with 40 editorially distinct entries per intent. Use stable IDs such as `request-001`; do not place private chat records in the catalog.
- [ ] Add `catalog.test.ts`: assert 160 unique IDs, 40 per intent, nonempty valid tags and text; assert each offered situation/intent/tone combination has at least three distinct choices. Review naturalness and tag correctness manually; these cannot be proved by counting words.
- [ ] Run both engine/catalog test files and `npm run typecheck`; commit the working catalog/engine with the lockfile. Setup failures are tooling failures, not the desired behavior-test failure.

## Task 2: Local preferences and saved ideas

**Files:** `src/features/preferences/storage.ts`, `storage.test.ts`.

**Interfaces:** consumes `Selection` and `ResultSnapshot`.

- `Favorite = ResultSnapshot & { savedAt: number }`.
- `Preferences = { selection: Selection; soundEnabled: boolean; motionMode: 'system' | 'paused' | 'full' }`.
- `StoredState = { version: 1; preferences: Preferences; favorites: Favorite[] }`.
- `StorageAdapter = { read(): { state: StoredState; persistent: boolean; canWrite: boolean }; write(state: StoredState): { persistent: boolean } }`.
- `createStorageAdapter(storage: Pick<Storage, 'getItem' | 'setItem'> | null): StorageAdapter`; key `klets.state`. A reader returning `canWrite:false` must not overwrite an unknown version.

- [ ] Write `storage.test.ts`: `deniedReadUsesSession`, `deniedWriteKeepsSessionState`, `unknownVersionIsNotOverwritten`, `malformedStateDoesNotCrash`, `duplicateFavoriteKeepsOriginalSnapshot`. Assert denied storage returns `persistent:false`; existing raw unknown-version bytes remain unchanged.
- [ ] Run the storage test file and verify expected behavior failures.
- [ ] Implement validated reads, safe version-1 writes and memory fallback. Keep unknown/unreadable data intact; no cloud, encryption claims or migration of formats that do not exist.
- [ ] Run Task 2 tests and typecheck; commit the adapter and tests.

## Task 3: Generator controller and complete supporting flows

**Files:** all controller/UI files listed above. Add `src/test/setup.ts` for DOM tests.

**Interfaces:** consumes Task 1 selection/reservation and Task 2 storage.

- `GeneratorState = { selection: Selection; current: ResultSnapshot | null; pending: ResultSnapshot | null; phase: 'idle' | 'running'; notice: string | null }`.
- `useGenerator({ catalog, storage, random, now }: { catalog: readonly Idea[]; storage: StorageAdapter; random: () => number; now: () => number })` returns `{ state, preferences, favorites, persistence, activate, publish, finish, setIntent, confirmContext, finalizePending, copyCurrent, saveCurrent, removeFavorite, undoRemoval, setFeedback }`.
- `activate(): boolean`; `publish(actionId: string): void`; `finish(actionId: string): void`; `setIntent(intent: Intent): void`; `confirmContext(selection: Selection): void`; `finalizePending(): void`.
- `copyCurrent(): Promise<void>` and `saveCurrent(): void` capture displayed snapshots at invocation; a late status cannot attach itself to a different result.
- `removeFavorite(ideaId: string): void`; `undoRemoval(): void`; `setFeedback(patch: Pick<Preferences, 'soundEnabled' | 'motionMode'>): void`. `persistence` describes durable versus session-only state; the controller exposes the persisted preferences/favorites without a second owner of those values.
- `SupportRoute = { view: 'context' | 'intent' | 'room-check' | 'saved' | 'settings'; returnTo: SupportRoute | null }`; shell stores the focus opener separately from serializable data.
- `PlayStage` will consume `{ actionId: string | null; running: boolean; motionMode: Preferences['motionMode']; soundEnabled: boolean; onActivate(): void; onContact(actionId: string): void; onSettled(actionId: string): void }`.

- [ ] Write `generator.test.tsx`: reserve under selection A, switch to B, publish twice and assert one result still carries A; assert duplicate activation while busy is ignored; empty pools retain old text and create no pending action. Also cover copy rejection/manual selection, in-memory save status and deduplicated favorites.
- [ ] Test supporting flows: immediate category selection; confirmed/canceled context drafts; finalization before opening a pane or hiding the tab; focus opener/fallback; Escape and internal browser Back; appreciation room-check omits assignment wording. Test removing a saved idea and undoing that removal once.
- [ ] Run the generator tests to verify meaningful failures before implementation.
- [ ] Implement controller-owned snapshots, route/focus handling and DOM result/actions. Render the optional momentcheck with intent-specific text from the spec. Before first draw keep copy/save/check inactive with clear explanation. Keep only one supporting view active.
- [ ] Run Task 3 tests, typecheck and prior behavioral tests once; commit the complete functional flow. No Stage dependency is required to test a result.

## Task 4: Signature 3D object and authored animation

**Files:** stage files and deterministic fallback asset listed above.

**Interfaces:** consumes the `PlayStage` props from Task 3; produces a lazy-loaded stage.

- `StagePose = { handProgress: number; bodyScaleX: number; bodyScaleY: number; bodyRotation: number }`.
- `samplePose(elapsedMs: number, reduced: boolean): StagePose`.
- `createActionTimeline(actionId: string, callbacks: { onContact(actionId: string): void; onSettled(actionId: string): void }, reduced: boolean): { advance(elapsedMs: number): StagePose; finalize(): void }`. Contact starts at 150 ms and settled at 600 ms; `finalize()` emits any outstanding callbacks once. Reduced mode finalizes without travel. Sound is a separate stage-owned optional cue; finalization due to interruption is silent.
- `createStage(canvas: HTMLCanvasElement): { render(pose: StagePose): void; resize(width: number, height: number): void; dispose(): void }`.

- [ ] Write `timeline.test.ts`: normal contact at 150–190 ms; recovery settles by 600 ms; paused/reduced mode has no hand travel; contact/settled callbacks for one action are idempotent even when canceled or resumed.
- [ ] Run timeline tests to establish behavior failures.
- [ ] Create a small orthographic Three.js scene with an authored, clothed rear and simplified hand; cap pixel ratio at 1.5, use broad warm/cool lighting, no live shadow maps, postprocessing or physics. The material must read as candy-like volume; keep seams and clothing coupled to the deformation group. Lazy-load the scene so content renders independently.
- [ ] Connect one timing owner to controller callbacks. Pause idle on hidden tab/supporting view and dispose observers, RAF, meshes, materials and renderer on unmount. Use a real DOM button named `Nieuw passend idee`, with canvas hidden from assistive technology.
- [ ] Create and inspect the fallback asset before committing it. If raster generation is used, preserve its prompt/provenance; if a rendered 3D still is used, preserve the reproducible scene. Handle init/context failure without losing the DOM button or inspiration: fallback activation publishes and settles its pending action immediately once, without waiting for missing 3D callbacks. Lazy-loading uses the same usable fallback until initialization succeeds. Sound remains off until explicit opt-in, uses one soft contact cue and never blocks a draw.
- [ ] Run timeline tests, all behavior tests and build; commit the stage. Visual asset quality and context-loss handling are recorded for Task 5, rather than falsely inferred from unit tests.

## Plan self-review

Coverage: catalog/filtering → Task 1; persistence → Task 2; generator/room-check/favorites/focus → Task 3; contact/motion/fallback → Task 4; responsive/readability/visual craft → Task 5; repeatable validation → Task 6. Both role perspectives are preserved through message meaning and intent-specific checks; a separate sub app remains future scope. Later points and agreements keep separate models.

The pure interfaces are stable across tasks; controller-owned action IDs separate result correctness from animation callbacks. Five likely failure classes in Review Focus each map to a owning task. Test steps target meaningful behavior; no screenshot treadmill or decorative mirror tests are prescribed.

Execution method: retain the user's request for parallel expertise. Independent content/stage/UI work may use narrowly scoped agents after interface decisions are fixed; integration and acceptance remain owned by the coordinating agent. Review this written plan before execution, as required by the selected Superpowers workflow.
